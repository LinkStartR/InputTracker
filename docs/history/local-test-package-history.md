## 为什么本地有 30 个包

这是“每轮实现提交 → 独立自包含发布目录 → 等待用户实际操作反馈”的本地测试链，而不是 30 个 Git 分支。8 月曾多次推送 GitHub 失败，随后用户明确要求先保证本地可运行，确实解释了远端同步停滞；但包持续增加的直接原因是每轮人工测试要隔离二进制与运行数据。例如托盘退出连续四轮修复、设备名称连续三轮修复。Git 提交已保存大部分产品变化，发布包还额外保存了当时的二进制与可能独有的 `data/`、`backups/`；Git 不能凭源码自动还原这些历史运行数据。

## 发布文件与运行数据核对

清理前的只读盘点显示，每包有 484 个发布文件，30 包的发布文件共约 6.224 GB（十进制，不含 `data/`、`backups/`、日志与设置等运行态文件）。#2 与 #3 的发布文件逐路径、长度和 SHA-256 完全一致；这是唯一经完整文件集比对确认的重复包。其余相邻包至少一个自有 DLL 的字节不同，但**哈希不同只能证明二进制不同，不能单独证明源码或功能变更**；同一源码再次构建也可能得到不同哈希。因此 #5、#6 仍保持“更新内容未证实”。

没有 `data/`、`backups/` 或设置文件的只有 #2、#3、#7、#8、#9、#18，共约 1.245 GB 发布文件。其余 24 包均含 `data/`；除 #1 外还存在设置文件，#25、#26 另含 `backups/`。最新的 #30 也有 `data/`，因此保留为当前测试目录。前 29 包仅发布文件部分合计约 6.017 GB；清理前未读取或比较任何运行数据内容。

## Git 与清理边界

截至 2026-09-21 编写本记录前，分支 `codex/ui-storage-integration` 相对本地保存的 `origin/codex/ui-storage-integration` 引用领先 73 个提交；本记录入库又增加一笔。该数量会随提交、抓取和推送变化，查看时应运行 `git rev-list --count origin/codex/ui-storage-integration..HEAD` 并核对真实远端状态。`.tools/.gitignore` 使发布包本身不进入 Git。本记录已进入本地 Git 历史；要把上述变化上传 GitHub，应对分支做非强制推送，而不是将约 200 MiB × 30 份二进制目录加入仓库。推送会同时更新现有分支/PR 的全部待推提交，不能说成“只上传说明文档”。

2026-09-23 已在确认 InputTracker 未运行、30 个目录与本文清单完全一致且没有链接目录后，将 #1–#29 逐项移入 E 盘回收站。复核结果为 29 条回收站记录、15,198 个文件、6,031,378,405 字节；每项均存在对应内容，源目录最终只剩 #30。#30 的 `InputTracker.dll` 前后 SHA-256 均为 `8567F13A2080417E8D5A8A10C9759BE14C9F3AE49E8656D70168E2E96B0FF58D`，`data/` 与设置文件仍在。旧包可能包含的 `.mspool`、`.mchunk`、`data/` 和 `backups/` 目前随目录保留在回收站中，可在清空回收站前恢复；移动到回收站本身不会释放 E 盘空间。Git 只保存本更新记录与源码提交，不保存这些历史二进制或运行数据。
